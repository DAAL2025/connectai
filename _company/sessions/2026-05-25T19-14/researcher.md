## 💾 D.AAL DESIGN: 시스템 진단 레퍼런스 데이터베이스 스키마 (v1.0)

**[스키마 목적]**
*   다양한 산업 및 기술 영역의 문제 사례를 표준화된 형태로 저장하고, 각 문제가 초래하는 재정적 손실(Failure Cost)을 정량적으로 제시하여 고객에게 위기감을 극대화하는 것이 목표입니다.
*   모든 데이터는 'Before (현재 상태)'와 'After (개선 후 기대치)' 비교 구조를 따릅니다.

### 1. `Case_Study` 테이블 (핵심 레퍼런스 정의)
가장 상위 단계에서 어떤 종류의 문제를 다루는지 분류하는 메타데이터입니다.

| 필드명 | 데이터 타입 | 설명 및 용도 | 근거/예시 값 | 필수 여부 |
| :--- | :--- | :--- | :--- | :--- |
| `case_id` | INT (PK) | 고유 사례 식별자 | C001, C002... | ✅ |
| `industry` | VARCHAR | 산업 분야 (예: 이커머스, SaaS, 금융 등) | [근거: 지난 의사결정 로그] | ✅ |
| `system_module` | VARCHAR | 문제가 발생한 시스템 영역 (예: 결제 플로우, 회원 관리, 콘텐츠 배포) | [근거: sessions/2026-05-25T13-59/...] | ✅ |
| `failure_type` | ENUM | 문제의 근본적 유형 분류 (기술 부채, 운영 리스크, UX 실패 등) | [근거: Self-RAG] | ✅ |
| `source_ref` | VARCHAR | 레퍼런스 출처 (경쟁사 A 분석, 자체 진단 체크리스트 v3.0 등) | [근거: 모든 메모리] | ✅ |

### 2. `Problem_Definition` 테이블 (문제 정의 및 실패 비용 정량화)
실패의 원인과 그로 인해 발생하는 재정적 손실을 구체적으로 명시하는 핵심 단계입니다.

| 필드명 | 데이터 타입 | 설명 및 용도 | 근거/예시 값 | 필수 여부 |
| :--- | :--- | :--- | :--- | :--- |
| `problem_id` | INT (PK) | 고유 문제 식별자 | P001, P002... | ✅ |
| `case_fk` | INT (FK) | 연결된 `Case_Study.case_id` | C001 | ✅ |
| **`pain_point_description`** | TEXT | 고객이 느끼는 불편함/불안감 정의 (정성적 측면) | "결제 성공 직후, 재시도 버튼을 찾지 못해 이탈합니다." [근거: Self-RAG] | ✅ |
| **`failure_cost_quantification`** | DECIMAL(15, 2) | **예상되는 직접적인 금전적 손실액 (₩ 단위)**. 가장 중요한 필드. | ₩50,000 (평균 이탈 고객당 예상 매출) [근거: 지난 의사결정 로그] | ✅ |
| `failure_cost_scope` | VARCHAR | 손실이 발생하는 범위 또는 빈도 (예: 트래픽 대비 15%, 월 평균 3천만원) | "월간 $20,000 상당의 미전환 매출" [근거: Self-RAG] | ✅ |
| `root_cause` | TEXT | 문제가 발생한 근본 원인 (예: 아키텍처 비효율성, 법적 규정 미반영) | "결제 게이트웨이와 백엔드 간의 상태 동기화 실패" [근거: sessions/2026-05-25T13-59/] | ✅ |

### 3. `Solution_Plan` 테이블 (개선 항목 및 로직 설계)
문제 해결을 위한 구체적인 기술적, 운영적 개선 방안입니다.

| 필드명 | 데이터 타입 | 설명 및 용도 | 근거/예시 값 | 필수 여부 |
| :--- | :--- | :--- | :--- | :--- |
| `solution_id` | INT (PK) | 고유 해결책 식별자 | S001, S002... | ✅ |
| `problem_fk` | INT (FK) | 연결된 `Problem_Definition.problem_id` | P001 | ✅ |
| **`improvement_item_description`** | TEXT | **구체적으로 개선해야 할 항목/기능**. 기술적 스펙 수준으로 작성. | "결제 실패 시, 즉시 재진단(Retry) UI를 팝업하고 오류 코드를 표시하는 시스템 구현." [근거: self-RAG] | ✅ |
| `required_module` | VARCHAR | 필요한 개발 모듈 또는 컨설팅 영역 (예: API 연동 레이어, 사용자 여정 플로우 재설계) | "Failure Cost 위젯 통합" [근거: sessions/2026-05-25T17-44/] | ✅ |
| `implementation_difficulty` | ENUM | 구현 난이도 (Low / Medium / High) | [근거: 전문 컨설팅 기준] | ✅ |

### 4. `ROI_Projection` 테이블 (가치 입증 및 수익성 예측)
해결책을 도입했을 때 예상되는 금전적 가치를 계산하여 고객의 구매를 유도합니다. 이 단계는 보고서의 설득력을 결정짓습니다.

| 필드명 | 데이터 타입 | 설명 및 용도 | 근거/예시 값 | 필수 여부 |
| :--- | :--- | :--- | :--- | :--- |
| `roi_id` | INT (PK) | 고유 ROI 식별자 | R001, R002... | ✅ |
| `solution_fk` | INT (FK) | 연결된 `Solution_Plan.solution_id` | S001 | ✅ |
| **`estimated_value_reclaim`** | DECIMAL(15, 2) | **예상 회수 가치**: 개선으로 인해 확보할 수 있는 매출액 또는 비용 절감액. (최대 재정적 이익) | ₩80,000 (이탈 고객의 75% 전환율 예상 시) [근거: Self-RAG] | ✅ |
| **`estimated_investment_cost`** | DECIMAL(15, 2) | 개선에 필요한 투입 비용 (컨설팅 및 개발비). | ₩300,000 (시스템 감사 요청 단계 비용) [근거: 지난 의사결정 로그] | ✅ |
| **`calculated_roi`** | CALCULATED | **ROI = (회수 가치 - 투자 비용) / 투자 비용**. 수익률(%)로 계산하여 제시. | 166% (매우 높음) [근거: 모든 컨설팅 자료] | ✅ |
